# A-ONE 予約システム — 開発時の恒久指針

会話履歴がリセットされても、ここを起点に判断してください。
(ASMS = 福岡キッズカートアカデミーの予約システムとは **別プロジェクト**です。
インフラの流儀は揃えていますが、DB もワーカーも独立しています)

## v1 の中心思想 (仕様 20)

* 通常ルールはシステムが自動判定する。
* **最終的には現場・管理者の判断を優先できる。**
  → `forced = true` があらゆる判定を上書きする。この逃げ道を塞がないこと。
* 利用者は「今日走れる？ → 空きを見る → 予約 → 自分で変更 → 来場」を簡単に。
* A-ONE 側は「予定を登録 → 予約を受ける → 調整 → 天候対応 → 顧客フォロー」を
  1 つの管理画面で完結させる。

## 絶対に守る設計判断

### 1. 受付ルールの実装は SQL 側だけ

`db/0003_availability_engine.sql` の `aone_check_availability()` /
`aone_day_state()` が唯一の正。画面・API は結果を表示するだけ。

**TypeScript 側に「クラス上限」「RP は 2 組まで」などを再実装しない。**
表示と実際の受付判定がズレるのが、この種のシステムで一番タチの悪いバグ。

ルールを変えるときは:
1. `_TEST_rules.sql` に落ちるテストを足す
2. `0003` を直す (または新しい連番マイグレーションで `create or replace`)
3. テストを通す

### 2. 予約台帳は 1 本 (仕様 13)

Web / 電話 / 店頭 を別テーブルにしない。`aone_reservations.source` で
入力経路だけを記録する。だから電話予約を入れた瞬間に Web の空きが変わる。

### 3. 二重予約は DB で止める

`aone_create_reservation()` は日付単位の `pg_advisory_xact_lock` を取ってから
空き判定 → INSERT する。API 層でのチェックはあくまで UX 用。

### 4. 予約者専用 URL がログインの代わり (仕様 10)

`access_token` (UUID v4) を知っていること = 本人。パスワードもマジックリンクも
作らない。ID だけを知っていても中身は見えないようにする
(`/reserve/complete/[id]` は `?t=` の一致を必須にしている)。

将来メールアドレスでの本人確認が必要になったら、ASMS と同じ Supabase Auth
Magic Link を足す。**電話番号だけをキーにした顧客検索 API は作らない**
(推測可能な値で PII を開けてしまうため。ASMS と同じ禁則)。

### 5. 天気予報で自動中止にしない (仕様 8)

気象庁 JSON は管理画面の **参考情報**としてのみ表示する。営業状況を変えるのは
`/admin/day/[date]` か `/admin` のワンタップで人が押したときだけ。

**営業状況と路面状況は別の列**にしてある (`db/0021_...sql`)。
1 本にまとめると「営業しているが路面はウェット」が表せない。

* `business_status` … `open` / `checking` / `cancelled` (走行中止) / `closed` (休業)
  既定は `open`。**`cancelled` と `closed` は予約を止める**
* `surface_status` … `dry` / `wet` / `drying` / `heavy_wet`。`null` = 未設定
  **表示だけ。受付可否には一切影響しない**ので、判定関数から参照しないこと

臨時休業を予定 (`aone_blocks` の `kind='closed'`, `scope='all'`) として
登録してあれば、`aone_day_state()` が営業状況を自動で `closed` にする
(`business.source = 'block'`)。予定と当日表示を二重に入力させないため。
その日に手で別の状況を設定してあれば、手の設定が勝つ。

### 5.0 「今日走れる？」は時間帯で出し分ける (2026-08 オーナー確認)

営業状況 (`business_status`) は日の属性で、時計とは関係ない。
一方トップページは「**いま**行って走れるか」を見る画面なので、
19 時に「営業中」と出ていると嘘に見える。そこで時間帯を重ねて出す
(`dayFocus()` / `openBadge()` / `openNote()` — `lib/domain.ts`)。

| 時刻 | 主役の日 | バッジ | 添える 1 行 |
|---|---|---|---|
| 〜 コースオープン (8:30) | 当日 | 準備中 🕗 | 本日は 8:30 コースオープンです |
| コースオープン 〜 クローズ (17:30) | 当日 | 営業中 🏁 | — |
| クローズ 〜 切替 (18:00) | 当日 | 本日は終了 🌙 | — |
| 切替 (18:00) 〜 24:00 | **翌日** | 準備中 🕗 | 明日は 8:30 コースオープンです |

切替時刻は **コースクローズの 30 分後**。`aone_settings` の営業時間を変えれば
一緒に動くので、設定項目を増やしていない。日付をまたげば自然に
「当日の準備中」に戻る (0:00〜8:30)。

* **臨時休業・走行中止のほうが強い。** その日は時間帯に関係なく休業・中止を出す
* **表示だけ。受付可否には一切かかわらない** (§1 のとおり判定は SQL 側が唯一の正)
* 同じ判定を `/`・`/api/public/today` (WordPress ウィジェット)・
  `/reserve/rp`・`/reserve/sport` の初期日付で共有する。
  18 時以降にフォームを開くと翌日が既定になる (選べる範囲は当日のまま)

### 5.1 状況を変えてもお客様には自動送信しない

**営業状況・路面状況を変えても、メールは 1 通も飛ばない。**
急な休みは電話で連絡する運用のため (2026-08 オーナー確認)。
`/api/admin/day` は一切メールを送らない — ここに自動送信を足さないこと。

お知らせが要るときは人が送る。送り口は `/api/admin/broadcast` の 1 本だけ:

* `reservation_ids` なし … その日の予約者全員へ (一括連絡)
* `reservation_ids` あり … 指定した予約者だけへ (個別連絡)

一括と個別でテンプレートを分けない (2 か所に書くと必ず片方が腐る)。
メールアドレスが無い相手には送れないので、画面側は「お電話でご連絡ください」と
電話番号を出す。

### 5.2 公開 API に管理用の項目を出さない

`aone_day_state()` は管理画面と共用なので、スタッフメモ・非公開の予定・
予定のメモがそのまま入っている。`/api/availability` は誰でも叩けるので、
`publicView()` で公開してよい項目だけに絞ってから返している。
day_state に項目を足すときは、ここに素通りしていないか必ず確認すること。

### 6. キャンセルは受け付けたうえで料金フラグを返す (仕様 9)

キャンセル規定 (2026-08 改定): **当日・ご連絡のないキャンセル (無断キャンセル)
のみ料金 100%**。連絡さえあれば、当日でも・種別を問わずキャンセル料なし。

したがって `cancel_fee` は `no_show` かどうかだけで決まる
(`db/0014_pricing_and_cancel_policy.sql`)。お客様が専用ページから自分で
キャンセルしたものは「連絡あり」なので、当日でも料金は発生しない。
無断キャンセルは `status = 'no_show'` で記録し、顧客サマリに出す。

請求するかどうかは最終的に現場判断。予約をブロックして
「電話してください」にはしない。

`aone_settings.rp_cancel_deadline_hours` は使わなくなった (列だけ残してある)。

### 7. 折り返しが必要な予約は落とさない

「連絡待ち (`contact_wait`)」「確認中 (`checking`)」は A-ONE から連絡しないと
確定しない。ここを落とすと失注に直結するので、3 か所で拾えるようにしてある:

* 受付時の管理者メール … 件名が `🔴要折り返し` で始まる (確定は `✅確定`)
* 管理画面 … `/admin` と `/admin/day/[date]` に未対応の件数と電話番号を出す
* 毎朝 8:00 の cron … 24 時間たっても未対応のものを 1 通にまとめて管理者に送る

対応の記録は**ステータスとは別**に `contacted_at` で持つ
(電話はしたが返事待ち、という状態があるため)。「📞 電話で対応済」ボタンで付き、
`aone_pending_callbacks()` の対象から外れる。

お客様宛のメールも、未確定のときは件名を
`【まだ確定していません】` にして 48 時間以内に折り返す旨と電話番号を出す。

### 7.1 お客様宛の自動メールはレンタルだけ (2026-08 オーナー確認)

`/api/cron/mails` が送る 3 通は **レンタル (RP・貸切・ナイター) のみ**。
持ち込みのスポーツ走行には送らない — 常連の方が何度も走りに来るので、
毎回リマインドとお礼が届くとうるさいだけになる。

| 種類 | いつ | 対象 |
|---|---|---|
| reminder | 前日 (朝の回) | 翌日のレンタル予約 |
| thanks | 当日 (夕の回) | その日のレンタル予約 |
| followup | **3 か月後** (朝の回) | 3 か月前のレンタル予約 |

* 二重送信は `aone_reservations.*_mail_sent_at` で防ぐ。**判定は必ず DB 側**で持ち、
  cron 側のスケジュールに依存させない
* 送信済み列があるので**さかのぼって拾っても二重にならない**。cron が 1 回
  落ちたときのために thanks は 2 日ぶん、followup は 3 日ぶん見る。
  リマインドだけはさかのぼらない (当日になってから前日の案内は届けられない)
* 3 か月前の日は `addMonths()` で出す。足した先に同じ日が無ければ月末に丸める
  (5/31 → 2/28)。丸めないと 2 月ぶんが誰にも届かない
* 1 通ごとの成否と失敗理由は `aone_mail_log`、cron 1 回ぶんの集計は
  `console.log('[cron/mails] …')` に残る

### 8. 当日と直前の受付制限 (2026-08 オーナー確認)

* 貸切 … カート **5 台以上**から / **当日は受け付けない** (前日まで)
  * `charter_type = 'with_karts'` … レンタルカート付き。従来どおり自動計算
  * `charter_type = 'course_only'` … コースのみ。**金額を出さず、必ず確認中 (折り返し)**。
    台数の概念が無いので最小台数のルールは適用しない
* 当日の RP … **17:00 以降の開始は不可** / **2 時間後以降**のお時間のみ

すべて `aone_check_availability()` に入れてある。ここに入れておけば Web
フォーム・管理画面・予約者ページの変更のどこから来ても同じ判定になり、
管理者は `forced = true` で従来どおり上書きできる (電話で個別対応する余地を残す)。

台数を見る必要があるため `p_vehicles` を引数に足している。引数を増やすときは
**古いシグネチャを drop してから** 作ること。残っていると 8 引数の呼び出しが
古い関数に解決され、新しいルールが効かない。

### 8.2 毎週の定休は曜日で持つ (2026-08 オーナー指示)

「日曜日の午後はスポーツ走行を基本受けない」のような、**日付ではなく曜日で
決まる決め事**は `aone_weekly_sport_closed (dow, session)` に持つ
(`db/0026`)。0 = 日曜。判定は `aone_check_availability` の中。

ブロック予定 (`aone_blocks`) で毎週ぶんを登録する運用にすると、必ずいつか
入れ忘れる。登録しっぱなしで効き続ける形にしてある。

* **止めるのはスポーツ走行だけ。** RP・貸切・ナイターは通常どおり受ける
  (日曜午後こそレンタルのお客様が来る時間帯)
* 「基本」なので、管理者は `forced = true` で今までどおり入れられる
* すでに入っている予約は消えない (§8.1 と同じ)
* 表示は `closed` = 「✕ 受付停止」。`off` (— 対象外) にはしない
  — お休みは対象外ではなく、その枠を受けていないだけ
* 設定は `/admin/settings` の 曜日 × 午前/午後 のチェック。
  送られてきたものが全量なので、API は消してから入れ直す
  (差分を計算すると必ずズレる)

> `_TEST_rules.sql` は冒頭で出荷時の既定を確かめてから
> `aone_weekly_sport_closed` を空にする。ここを残すと、日曜を使う他のグループが
> 道連れで落ちる。毎週のお休みそのものは 24 群で試す。

### 8.1 受付停止の予定は「これから受ける予約」にしか効かない

`aone_blocks` は `aone_check_availability()` から見るだけ。
**あとから予定を足しても、すでに入っている予約は消えないし取り消されない。**
だから「先に停止してから強制で入れ直す」ような手順は要らない
(2026-08 オーナーからの質問)。予約を消したいときは予約側で取り消す。

停止範囲 (`scope`) は 2 方向ある。**止めたいものを数えるか、走らせたいものを数えるか**
で使い分ける:

* `category` … 指定した 1 カテゴリーだけ止める
* `only_category` … `allow_categories` に入れたカテゴリー **だけ** 受け付け、
  ほかのスポーツ走行を止める (`db/0024`)

レース前日の「カートはそのまま・ミニバイク等は弾く」は `only_category` に
カートを入れる。`category` を 3 件登録する形だと、あとでカテゴリーが増えたときに
足し忘れて「止めたいものが走れてしまう」事故になる。

`allow_categories` が空のときは **何も止めない**。登録し忘れで全部止まるより、
何も起きないほうが実害が小さい。ただし黙って何も起きないと気づけないので、
`/admin/day/[date]` の一覧に「⚠ 走れるカテゴリーが未選択です」と出す。

**予定は後から編集できる** (`/api/admin/block` の `action: 'update'`)。
停止範囲を間違えて登録すると「全部止まったまま」になり、削除して作り直すと
参加申込の設定まで消えるため。日付だけは変えない (別の日に動かすのは
消して登録し直すほうが分かりやすい)。

編集フォームには元の行が要るので、`/admin/day/[date]` の予定一覧は
`aone_day_state()` の blocks ではなく `blocksOfDay()` でテーブルを直接読む
(day_state の blocks は表示用に絞ってあり `allow_categories` が入っていない)。

### 9. イベントの参加申込は別台帳 (2026-08 オーナー指示)

レース・イベントの**参加申込 (エントリー)** も予約システムで受ける。
ただし `aone_reservations` には入れず、`aone_event_entries` に分けてある。
§2「予約台帳は 1 本」の例外なので、理由をはっきり書いておく:

* 聞く項目がまったく違う (チーム名・ゼッケン・参加クラス・フレームメーカー)
* **走行枠を消費しない。** イベント日はブロック予定が終日止めているので、
  エントリーが何件入っても受付可否は変わらない
* 「1 チーム 20,000 円」と「1 人 7,000 円」が混ざり、人数 × 単価で出せない

**顧客だけは共通** (`aone_upsert_customer`)。レースに出た人が普段も走りに
来るのがふつうなので、顧客台帳が割れると顧客サマリが役に立たなくなる。

申込の様式は 3 つ (`entry_type`):

* `sprint` … スプリント (レンタルカート)。人単位。7,000 円/人
* `endurance` … 耐久 (レンタルカート)。チーム単位。代表者 1 名。20,000 円/チーム
* `series` … RMC (マイカート)。人単位。フレームメーカー・希望ゼッケン・参加クラス

**参加クラスは RMC だけ**。レンタルカートの耐久・スプリントにクラス分けは無いので、
`/admin/calendar` でも `series` を選んだときだけ選択肢を出す。

**開催日はカレンダーの予定そのもの。** `/admin/calendar` で予定を登録するときに
「参加申込を受け付ける」を入れると、その予定が `/reserve/event` に出る。
日付を二度入力させない (§19 と同じ考え方)。

**参加費はイベントごとに入力する** (2026-08 オーナー確認)。クラスや年で変わるため。
`entry_price` が null なら金額を出さずに受け付け、A-ONE から折り返す
(貸切の「コースのみ」と同じ扱い)。

**参加案内の自動送信はしない。** 集合時間・組み合わせ・レンタル車両の割り当てが
毎回違って定型化できないため。申込直後の控えだけ自動で送り、あとは
`/admin/entries` から人が連絡する。

> ⚠️ **新しいテーブルを足したら grant を書くこと。**
> `0005` の `grant all on all tables in schema public to service_role` は
> **その時点で存在したテーブルにしか効かない。** 忘れると管理画面が
> `permission denied` で落ちる (0022 で実際に踏んだ)。

## カテゴリーごとの「予約が必要か」 (2026-08 オーナー確認)

* **カート / ミニバイク**: 予約なしの飛び込みで走れる → 「走れます」と表示
* **キッズカート / その他 (大型バイク等)**: 事前予約が必要 → 「要予約」と表示

`aone_categories.requires_reservation` で保持し、`/admin/settings` から変更できる。
「今日走れる？」で全部を一律「走れます」と出すと、キッズで来場した人が走れない
事故になるため、この区別は消さないこと。

飛び込みはシステムに載らないので、クラス数の計算には入らない。実際に何クラス
走っているかの最終判断は現場側にある (強制受付・受付停止で調整する)。

## 環境変数の source of truth (ASMS と同じ流儀)

**wrangler.jsonc の `vars`** — 非機密の source of truth。

> ⚠️ `vars: {}` や `vars` キーの省略は、deploy 時に Dashboard の非機密変数を
> **全削除**する (ASMS で 3 回事故)。常に全キー入りで維持すること。

**Cloudflare Dashboard「変数とシークレット」(シークレット型のみ)**:
`SUPABASE_SERVICE_ROLE_KEY` / `RESEND_API_KEY` / `CRON_SECRET` /
`ADMIN_PASSWORD_HASH`。追加後は「デプロイ タブ → 現バージョン再展開」で
bind し直す。

> ⚠️ **このリポジトリは公開 (public)**。`wrangler.jsonc` に書いたものは
> 誰でも読める。管理画面のパスワードハッシュを vars に置くと、オフラインで
> 総当たりできてしまうのでシークレット型に置く。`PUBLIC_SUPABASE_ANON_KEY`
> は公開前提のキーなので vars で問題ない (RLS で守る)。

## 商品構成と料金 (2026-08 オーナー確認)

**レンタル** = レンタルカートを使うもの
* RP (レースパック) — 6,600 円 / 人。練習 → 予選 → レース、表彰台で記念撮影
* 貸切 — 11,000 円 + 11,000 円 × カート台数 (最小 5 台 = 66,000 円)
* 通常のレンタル走行 — 1 ヒート 2,200 円 / 7 分。**予約不要**なのでシステムに載せない
  (「今日走れる？」で営業状況だけ見せて、あとは来場してもらう)

**ナイター** = レンタルのみ (レースパック または 貸切)
* 持ち込み車両のナイター走行は受け付けない
* 常に要相談 (`status = 'checking'`)。営業時間外なので自動判定はしない
* 内訳は `aone_reservations.night_kind` ('rp' / 'charter')。料金も同じ計算で入る

**スポーツ走行** = 持ち込み車両 (カート / ミニバイク / キッズカート / その他)
* カート・ミニバイクは予約不要で走れる
* キッズカートは管理画面からのみ予約を受ける (`admin_only`)

料金は `aone_settings` に持ち、計算は `aone_auto_amount()` の 1 か所だけ。
作成時は `aone_fill_amount()`、人数・台数の変更時は `aone_recalc_amount()` が
これを呼ぶ (同じ式を 2 か所に書くと必ずズレる)。

**手入力かどうかは `amount_manual` 列で持つ。** 立っている間は自動計算で
上書きしない。フラグが立つのは「**自動計算と違う金額**を入れたとき」だけ。

この判定は 2 回間違えている。同じ轍を踏まないこと:

* 0016 … 「変更前の金額が自動計算と一致するか」で推測した
  → 一度ズレた行が永久に手入力扱いになり、二度と直らない
* 0017 … 「金額が変わった UPDATE」をすべて手入力とみなした
  → 0017 自身の一括修正がトリガーを踏み、直した行を全部手入力にした

金額を自動計算に揃える UPDATE でフラグが立ってはいけない、が要点。

単価を `/admin/settings` で変えても**過去の予約の金額は変わらない**。
次にその予約を変更したとき、手入力でなければ新しい単価で計算し直される。

カレンダー (公開 / 管理) には「レンタル / スポーツ走行 / 両方」の切り替えがある。
お客さんが「レンタルで遊ぶ人」と「マイマシンを持ち込む人」にはっきり分かれるため。
レース・イベント・臨時休業はどちらのモードでも表示する。

**選んだモードは localStorage に覚えさせる** (2026-08 オーナー確認)。
ただし「スポーツ走行」のまま開き直すと RP・貸切が出ないので、
**そのモードのときはカレンダーの下に「両方」への戻り方を出す**こと。
覚えるのをやめると毎回押し直しになるので、注記のほうで解決する。
ページ側の `data-mode` は覚えたものより優先する。

月の移動は 3 か所で同じ形にしてある (`monthOptions()` が唯一の定義):
**見出しの年月そのものがプルダウン**で、3 か月前 〜 12 か月先から選べる。
前月・翌月ボタンだけだと「8 月に 12 月を見る」が 4 回押しになるため。

**スマホで今月を開いたときは今日から始める。** 1 日 1 行の縦長表示なので、
月初から並べると今日にたどり着くまでスクロールが要る。過ぎた日は
「▼ ○月1日〜○日 も表示する」でいつでも出せる。たたむのは
**今月だけ**で、過去の月は全部が過ぎているのでたたまない (空になってしまう)。
PC の 7 列は歯抜けになると読めないので、たたむのは
`@media(max-width:640px)` の中だけに書くこと。

## 予約者名の公開範囲

RP の予約画面に「この日のご予約」として時間と名前を出している
(旧 WordPress スケジュールが「AM10:00〜 RP パットリ様」と実名を出していた運用に合わせた)。

公開の粒度は `aone_settings.public_name_display` で切り替える:
`family` (姓のみ・既定) / `full` (入力どおり) / `hidden` (時間だけ)。

**公開側に出すのは 開始時間・人数・表示名だけ**。電話番号・メール・予約番号・
スタッフメモは公開 API に含めない。管理画面は設定に関係なくフルネームを出す。

公開カレンダー (公開スケジュール / WordPress ウィジェット) にも、RP・貸切の
「時間 + 表示名」を出す (旧 WordPress スケジュールと同じ運用)。粒度は同じ設定に従い、
`hidden` にすれば全部の公開面から名前が消える。

**「姓のみ」は名前そのものを見て決める** (`aone_public_name` / `db/0023`)。
種別で分けていた時期があるが、RP にも法人名・チーム名で入るため破綻した。

1. 法人・団体らしければ略さない … `(株)ふーぷーパートナーズ` / `A-ONE Racing` / `麻生工科大学`
2. 空白があれば先頭トークン … `山田 太郎` → `山田`
3. 漢字を含まなければ略さない … `エンドウ` (姓だけ入れた形)
4. 3 文字以下は略さない … `今井` / `佐々木`
5. それ以外は先頭 2 文字 … `山田太郎` → `山田`

> 実運用で `(株)ふーぷーパートナーズ` → `(株 様`、`エンドウ` → `エン 様` に
> なっていた。「空白が無ければ先頭 2 文字が姓」の決めうちが原因。

スポーツ走行の予約は公開面に一切出さない (走れるカテゴリーだけ出す)。

## 性能上の落とし穴

`aone_month_state()` の CTE は **`as materialized` が必須**。付けないと
下で `st` を参照するたびに `aone_day_state()` が再評価され、1 か月ぶんで
6 秒以上かかる (実測: 6.6 秒 → 0.64 秒)。カレンダー系の関数を触るときは
必ず `\timing on` で測ってからコミットすること。

`aone_day_state()` 自体は 1 日あたり 30ms 前後。月表示は API 側で
60 秒キャッシュしている。これ以上必要になったら、日別の集計を
マテリアライズドビューに落とすことを検討する。

## DB マイグレーション

* `db/000N_*.sql` は連番で追加のみ。既存ファイルの編集は fresh install の
  整合性維持が目的のときだけ (本番適用済みの意味を変えない)。
* 適用は Supabase SQL Editor で手動 (自動適用パイプラインは無い)。
* **アプリを先にデプロイし、そのあとで SQL を当てる。** 逆にすると、古いアプリが
  新しい `aone_day_state()` の形を読めずに公開ページが落ちる。新しいアプリは
  古い DB の形でも既定値で動くようにしておくこと (`queries.ts` の `withStatus`)。
* 祝日テーブルは毎年 2 月の官報告示のあと、翌年ぶんを新しい連番で追記する。

## 定時実行は Cloudflare Workers Cron Triggers (2026-08 移行)

`wrangler.jsonc` の `triggers.crons` は **毎時 1 本 (`0 * * * *`) だけ**。
何を回すかは `worker/index.js` の `scheduled` が JST の時刻で振り分ける
(`worker/tasks.js` の `tasksFor()` が唯一の定義)。

| JST | 回すもの |
|---|---|
| 08:00 | reminder + followup + callbacks |
| 12:00 | reminder (朝が落ちたときの拾い直し) |
| 18:00 | thanks |
| 毎月 1 日 09:00 | backup |

* **cron の本数を増やさない。** 時刻ごとに cron を足すと、プランの上限や
  「どれがどれ」で事故る。毎時 1 本 + 中で分岐なら、回を足すのは 1 行で済む
* `scheduled` は **自分自身の fetch ハンドラを呼ぶ** (外に出ないので速く、
  `CRON_SECRET` がネットワークに出ない)。基準 URL は vars の `CRON_ORIGIN`
* 二重送信は**必ず DB 側** (`*_mail_sent_at`) で止める。cron の回数や
  スケジュールに依存させない。だから同じ回を 2 度呼んでも安全
* 実行結果は `console.log('[cron] …')` に 1 行ずつ残る
  (Cloudflare の Worker ページ → **Observability タブ → ログ**。
  `observability.enabled` は true)。
  **送るものが無い時間も 1 行残す** — 何も出ないと「cron が動いていないのか、
  その時間は何も無いのか」が見分けられない
* 時刻から「何をやるか」を組み立てるのは `worker/tasks.js` の `planFor()`。
  JST への読み替えごとここに入れてあるので、Node からそのまま試せる
  (`worker/index.js` は cloudflare:* を読むので Node から import できない)

> ⚠️ **Astro の Cloudflare アダプタは `scheduled` を出せない。**
> `dist/_worker.js/index.js` は fetch ハンドラだけなので、`worker/index.js` が
> それを包んで `scheduled` を足し、`main` をそちらに向けている。
> `worker/index.js` の `fetch` には何も足さないこと — サイト全体が落ちる経路が
> 1 本増える。`npx wrangler deploy --dry-run` でバンドルの成否とサイズを
> 確かめられる (2026-08 時点で gzip 437 KiB)。

### cron が止まったら管理画面で気づく (2026-08 オーナー要望)

移行の理由が「黙って止まるのが怖い」なので、**動作確認を Cloudflare の
ログ頼みにしない**。毎時 `/api/cron/ping` が `aone_cron_log` に 1 行残し、
`/admin` の「自動メール」欄が `aone_cron_health()` を読んで出す。

* **送るものが無い回も記録する。** 記録が途切れたことが「止まった」の証拠になる
* 90 分あくと赤くなる (ふだんは毎時 0 分に入るので、1 回飛んでも赤にならない)
* 入れるのは「いつ動いたか」だけ。1 通ごとの成否と失敗理由は `aone_mail_log`
  (同じものを 2 か所に持たない)
* 記録に失敗しても cron 全体は落とさない — メールが送れているほうが大事
* `cronHealth()` は関数が無ければ `null` を返す。**0025 を当てる前でも
  管理画面は開ける** (欄が出ないだけ。§「DB マイグレーション」の
  「アプリを先にデプロイ」を守るため)

> ⚠️ **GitHub Actions の `schedule:` を復活させないこと。**
> 「リポジトリを 60 日さわらないと定時実行が自動で止まる」仕様があり、
> 運用が落ち着いた頃に黙って送信が止まる。これが移行した理由。
> `workflow_dispatch` (手動実行) だけは緊急時のために残してある。

## バックアップ

Supabase の無料プランに自動バックアップは無い。予約台帳と顧客名簿が飛ぶと
業務が止まるので、**毎月 1 日に CSV を管理者宛にメールで送る**
(`/api/cron/backup` ← Worker の cron。手動で欲しいときは
`.github/workflows/aone-backup.yml` を Actions タブから実行する)。
受信箱がそのまま保管場所になるので、誰かが手作業を思い出す必要がない。

CSV の列定義は `lib/csv.ts` の 1 か所だけ。管理画面のボタン
(`/api/admin/export`) と月次メールが同じ関数を呼ぶ
(2 か所に書くと落とした CSV と届く CSV が食い違う)。

送るのは **予約台帳・顧客名簿・参加申込の 3 本**。業務が止まるデータを
増やしたら、ここにも足すこと。

Excel で開けるように **UTF-8 BOM 付き**にしている。外すと日本語が化ける。
