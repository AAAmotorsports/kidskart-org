# A-ONE CIRCUIT 走行写真販売システム — 設計・費用提案書 (v2)

> **v2 (M0 確定)**: オーナー承認条件を反映。v1 からの変更点:
> - 二重購入: 決済前にサーバーで検証 (`photo_create_pending_order`)。万一の二重決済は `needs_review` に回し、管理者が確認・返金 (自動返金はしない)

> - Supabase は無料プランで開発し、本番前に Pro を判断。Stripe はテストモード、手数料は仮 3.6%
> - 売上試算は購入率 10 / 20 / 30% が基本、40% は好調ケース (§8-2 を差し替え)
> - 実装物: `db/0001_initial_schema.sql` (テスト付き)、`docs/SCREENS.md`、`app/` 雛形

## 0. 結論サマリ

| 項目 | 提案 |
|---|---|

```

  Safari/PWA                               QR → /g/{token}              /tv/{tvToken} (全画面)
   │ ①写真選択(100枚)                        │                            │ 30秒ポーリング
   │ ②ブラウザ内で                            │                            │ + localStorage キャッシュ
   │   原本(EXIF除去)/プレビュー(透かし)/       │                            │
   │   サムネ を生成                          │                            │
   │ ③署名付きURLでR2へ直接PUT                │                            │
```

### 技術選定の比較と推奨

| 論点 | 案A (推奨) | 案B | 理由 |
|---|---|---|---|
| 画像処理 | ブラウザ内 (Canvas) | Worker + Cloudflare Images / wasm | Workerは128MB・CPU時間制限があり12MP JPEGの透かし合成は不安定。Images変換は $0.5/1,000枚相当で費用が増える。iPhoneは性能十分 |
| HEIC | `<input accept="image/jpeg,image/*">` でiOSが選択時にJPEG変換 | サーバーでHEIC→JPEG | iOS標準挙動で解決。端末側設定「写真→転送：自動」のみ運用ルール化 |
| DB | Supabase (既存と流儀統一・将来の予約連携が容易) | Cloudflare D1 | D1は無料で最安だが、既存SQL資産/Auth/RLSの流儀と別物になる。連携を重視してA |
| フロント | **Astro + 小さなReact島** (既存 `aone/app` と同じ) | Next.js | CloudflareでのNext.jsは追加アダプタが必要で保守が重い。既存と揃える方が運用が楽 |
| 管理認証 | Supabase Auth メールOTP | Cloudflare Access | 既存と同方式。Basic認証は使わない(既存方針) |
| ZIP | Workerでストア(無圧縮)ストリーミングZIP | 事前生成してR2保存 | JPEGは圧縮不要でCPU僅少。保存コスト無し |

> 注意: 既存システムとは **リポジトリ内の別ディレクトリ `photo-sales/`** (または別リポジトリ) に置き、既存の予約テーブルには一切触れません。

## 2. 画面構成

### 2-1. お客様 (スマホ最優先) `/g/{token}`
1. **ヘッダー**: ロゴ / 利用日・走行時間 / 「写真は購入まで透かし入り」
2. **写真グリッド** (3列サムネ・無限スクロール・15秒毎に自動更新、準備中は「写真準備中です」)
3. **拡大ビュー**: スワイプ送り、♡で選択、購入済みは「ダウンロード」表示
4. **画面下固定カート**: 「3枚選択中 → ¥1,000」。**プラン選択を客に考えさせず、最安の組合せを自動計算**
   - 計算: `n枚 = floor(n/3)×1,000 + (n%3)×500` を `min(…, 全写真パック2,000円)` で上限
     (2枚=1,000 / 3枚=1,000 / 4枚=1,500 / 5枚以上は2,000円で「全写真パックがお得」へ誘導)
   - 3枚セット・全パックの価格は設定値。ルールは1関数に集約しテストする
5. **決済**: Stripe Checkout へ遷移 → 完了後 `/o/{orderToken}`
6. **購入完了/再DL** `/o/{orderToken}`: 写真ごとのDLボタン + 全部ZIP + 有効期限表示
7. 注意書き: 「このQRを持つ方は写真を閲覧できます。SNS等に公開しないでください」
8. 購入済み写真は選択不可 (重複購入防止)

> **iPhoneでの保存**: ZIPは「ファイル」アプリ保存になるため、写真単体は **Web Share API で「画像を保存」→写真アプリ** へ入れられる導線を用意。ZIPは補助。

### 2-2. スタッフ (iPhone) `/admin`
- **ダッシュボード**: 本日のグループ(状態: 準備中/公開中)・アップロード枚数・本日売上・購入件数
- **グループ作成** (1画面): 開始時刻(現在時刻を初期値)・団体名・人数・プラン・同意チェック(店内表示/オンライン掲載) → 作成直後に **QR表示画面** (画面提示 / 印刷ボタン)
- **アップロード**: 「写真を選ぶ」→ 100枚選択 → 自動で並列(3同時)処理。進捗バー・失敗は自動再試行(最大5回)・**画面を閉じても再開できるキュー(IndexedDB)**。撮影時刻(EXIF)で自動並び替え、SHA-256で重複スキップ
- **グループ詳細**: 写真グリッド、複数選択して削除/別グループへ移動、公開/非公開、TV表示に送る
- **TV管理**: 表示中グループ、自動/手動、スライド秒数、停止
- **売上**: 日別/月別、プラン別、グループ別、購入率、決済状況、返金、CSV
- **設定**: 価格、保存期間、スタッフ(admin / staff)、ロゴ、削除依頼対応

### 2-3. テレビ `/tv/{tvToken}` (全画面・操作不要)
- 最新アップロードのグループを優先 → 一定時間で次のグループへ
- 1グループ内: スライドショー (透かし・低解像度 1280px)。左下ロゴ、右下「**QRコードで写真購入**」案内文、グループ名/走行時間
- 同意済みグループのみ。ゼロ件時はロゴ+案内画面
- **オフライン耐性**: 直近の表示リストとプレビューを Service Worker / Cache でキャッシュ。通信断中はキャッシュで継続、復帰後自動更新。Wake Lock + 日次自動リロード
- tvToken は管理画面で再発行可能 (漏洩対策)

## 4. 写真アップロード・画像変換の実装方式

スタッフiPhone上のブラウザで1枚ごとに以下を実行 (Web Worker / `createImageBitmap` + `OffscreenCanvas`、メモリ配慮で3並列):

1. File取得 (iOSがHEIC→JPEGに変換して渡す)。SHA-256 計算 → 同グループ既存と一致ならスキップ
2. EXIFの撮影時刻のみ抽出 (並び替え用)、**位置情報は破棄**
3. 原本: 長辺そのまま・Canvas再エンコード JPEG q=0.92 (EXIF/GPS消去。画質劣化は視認不可) ※撮影日時以外のメタデータは保存しない
4. プレビュー: 長辺1280px + 斜め透かし(ロゴ/ A-ONE CIRCUIT) JPEG q=0.75 (~150KB)
5. サムネ: 長辺400px JPEG (~30KB)。一覧からの流用防止のためサムネにも薄い透かしを入れる
6. Worker API `POST /api/admin/uploads/presign` で3ファイル分の署名付きPUT URL取得 → R2へ直接PUT (Workerを大容量が通らない)
7. `POST /api/admin/photos/commit` でメタ登録 (サーバーで拡張子/MIME/サイズ/マジックバイト検証、キーはサーバー生成)
8. 失敗は指数バックオフで再試行、IndexedDBに状態保存 → 再読込後に再開

> リスクと対策: 「クライアントで透かしを作る」ため、悪意あるスタッフ端末なら透かし無しを置ける。スタッフは信頼済み前提とし、**プレビュー用キーは originals と別バケット・サーバー側でサイズ上限(長辺≤1600px)を検証**することで原本の流出を防ぐ。将来、Cloudflare Images等へ移行可能な構造にしておく。
> iOSブラウザでのメモリ上限が実機で問題になる場合は、並列数を下げ、撮影順にバッチ処理します (MVP初期に実機で必ず検証)。

## 5. Stripe決済と購入権限の管理方式

```
[お客様] 写真選択 → POST /api/g/{token}/checkout {photoIds[]}
 Worker: ①QRトークンからグループ特定 ②photoIdsがそのグループの公開写真か検証
         ③購入済み写真を除外 ④サーバーで金額を再計算 (クライアント金額は無視)
         ⑤orders(pending) 作成 + Stripe Checkout Session作成 (単一line item、metadata=order_id)
         ⑥Idempotency-Key = order_id で二重生成を防止
 Stripe → 決済 → success_url=/o/{orderToken}
 Stripe → Webhook checkout.session.completed
 Worker: 署名検証 → stripe_events に event_id INSERT (重複なら無視)
         → orders paid化 + order_items確定 (全パックは当時の公開写真IDを展開して固定)
         → download_expires_at 設定
 期限切れSession (expired) / payment_failed → failed 扱い、写真は解放
```

- **購入権限 = paid 状態の order_items** のみ。success_url に戻っただけでは権限を与えない (Webhook確定を待つ画面)
- ダウンロード: `GET /api/dl/{orderToken}/{photoId}` → Worker が `orders.status=paid` かつ期限内か検証 → R2から原本をストリーム (R2の公開URLは存在しない)。署名付き短命URL方式も可
- ZIP: `GET /api/dl/{orderToken}/zip` でストリーミングZIP
- 返金: 管理画面→Stripe Refund API→Webhook `charge.refunded` で状態更新、返金後はDL不可
- 同時決済の二重購入: Session作成時に未払pendingの写真を30分間ソフト予約せず、**Webhook確定時に重複が見つかった場合は自動返金**の方針を提案 (稀なケースで実装簡素)
- カード情報・PANは一切受け取らない。Apple Pay/Google Pay は Stripe Dashboard 設定とドメイン登録で有効化

## 6. 写真保存・自動削除の設計

| 対象 | 期限 (デフォルト・設定可) | 動作 |
|---|---|---|
| プレビュー/サムネ・グループ公開 | 撮影日から **30日** | 閲覧終了。ページは「公開期間が終了しました」 |
| 未購入の原本 | 撮影日から **30日** | 原本・プレビュー・サムネをR2から削除、`photos.status=deleted` |
| 購入済み原本 | `min(支払日+30日, 撮影日+60日)` | 期限7日前にメール/注文ページで告知 → 削除。注文ページに期限を常時表示 |
| 注文・売上記録 | **7年** (税務上の帳簿保存を要税理士確認) | 写真IDのみ残し、写真本体は残さない |
| 監査ログ | 1年 | |
| 非公開・削除依頼 | 即時 | 管理画面から グループ/写真を即非公開化→削除 (R2から物理削除+監査ログ) |

- **Cron Trigger (毎日 04:00 JST)**: 期限切れ検出 → R2 `DeleteObjects` → DB更新。冪等・再実行安全。失敗はログ+管理画面に警告
- R2 は Lifecycle ルールも併用 (保険): 例えば全オブジェクト 65日で自動失効

## 8. 初期費用・月額費用の試算

### 8-1. 前提 (すべて仮定。実績で見直し)
- 1グループ平均 **5名**、撮影 **80枚/グループ**
- 原本 **約3.2MB** (iPhone 12MP JPEG)、プレビュー **約0.15MB**、サムネ **約0.03MB** → 1枚あたり約3.4MB
- 保存は原則30日 → 常時保存量 ≒ 1か月分
- 購入率: **グループの40%** が1回購入、平均単価 **1,500円**
- 月間利用者 300 / 500 / 1,000人 → グループ数 60 / 100 / 200
- 為替 150円/USD
- 料金は2025〜2026年時点の公開料金を前提。**契約前に最新値を確認してください**

### 8-2. 試算 (月額) — 購入率 10 / 20 / 30% (40% は好調ケース)

「購入率」= 公開したグループのうち 1 件以上購入があった割合。平均注文額 1,500 円、Stripe 3.6% (仮) で試算。
システム費用は **本番で Supabase Pro を使う前提** (Workers $5 ≒ 750円 + Pro ≒ 3,750円 + R2 + ドメイン)。開発中の無料プランなら 約 800 円。

| | 300人 (60組) | 500人 (100組) | 1,000人 (200組) |
|---|---|---|---|
| 常時保存量 / R2費用 | 約16GB / 約13円 | 約27GB / 約38円 | 約54GB / 約100円 |
| システム費用 (Pro前提) | 約 4,500円 | 約 4,540円 | 約 4,600円 |
| 画像変換・R2転送 | 0円 | 0円 | 0円 |

月間の **売上 / Stripe手数料 / 差引** (差引 = 売上 − 手数料 − システム費用。撮影スタッフ人件費は含まない):

| 購入率 | 300人 売上 / 手数料 / 差引 | 500人 | 1,000人 |
|---|---|---|---|
| 10% | 9,000 / 324 / **約 4,200** | 15,000 / 540 / **約 9,900** | 30,000 / 1,080 / **約 24,300** |
| 20% | 18,000 / 648 / **約 12,800** | 30,000 / 1,080 / **約 24,400** | 60,000 / 2,160 / **約 53,200** |
| 30% | 27,000 / 972 / **約 21,500** | 45,000 / 1,620 / **約 38,800** | 90,000 / 3,240 / **約 82,200** |
| 40% (好調) | 36,000 / 1,296 / **約 30,200** | 60,000 / 2,160 / **約 53,300** | 120,000 / 4,320 / **約 111,100** |

## 9. セキュリティ・プライバシー上のリスク

| リスク | 対策 |
|---|---|
| QR漏洩/SNS共有で他人がプレビュー閲覧 | 128bitランダム、`noindex`、注意書き、写真は透かし付きのみ、必要なら管理画面でトークン再発行、公開期限 |
| 他グループ写真への不正アクセス | 全APIでトークン→group_id を必ず突合 (IDOR防止)、写真IDは連番にしない(UUID)、RLS全拒否 |
| 原本の直接URL取得 | 原本バケットは非公開、Worker経由のみ。プレビューと別バケット・別キー |
| 決済バイパス | success_urlで権限を与えない、Webhook署名検証、冪等性、サーバー再計算 |
| 総当たり (トークン推測) | 128bit + WAF/Rate Limit + 異常DL検知 (download_events) |
| 子どもの肖像・位置情報 | 同意管理 (店内表示とオンライン掲載を別々に)、EXIF/GPS除去、TVには同意済みのみ、**保護者向け同意文言を法務/オーナー確認**、削除依頼窓口 |
| スタッフアカウント乗っ取り | メールOTP、roleによる権限分離(返金・設定はadminのみ)、監査ログ、退職時の無効化 |
| 悪意あるファイル | MIME/マジックバイト/サイズ検証、再エンコードで無害化 |
| Webhook偽装 | Stripe署名検証、event_id重複無視 |
| 個人情報 (購入者メール) | Stripe保有を基本、自社DBは最小限。メールは領収・DL通知目的のみ |
| 削除漏れ | 日次Cron + R2 Lifecycle の二重化、失敗時アラート |
| TV画面を撮影され共有 | プレビュー(低解像度+透かし)のみ。同意済みグループのみ表示 |
