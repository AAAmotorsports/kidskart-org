# 月額固定費 0 円構成の検討 — Cloudflare Workers + D1 + R2

結論: **実現できる。固定費 0 円・従量費は月 約 0〜100 円 (R2 の保存量のみ)。**
ただし「無料枠のまま本番を回す」ことには 4 つの条件と 1 つの技術リスク (§3, §4) がある。
料金・上限は私が把握している公開情報に基づく。**契約・本番前に Cloudflare / Stripe / Resend の最新ページで確認すること。**

## 1. 構成

```
iPhone / スマホ / TV ──► Workers (Astro SSR + API)  ──► D1  (注文・グループ・写真メタ)
                              │   cron (毎日 JST 4:00)  ├─► R2 originals (非公開)
                              │                         ├─► R2 previews  (非公開、Worker 経由)
                              ├─► Stripe Checkout        └─► R2 backups   (D1 日次ダンプ)
                              └─► Resend (メール)
```
* スタッフ認証: メールで届くログインリンク + Cookie セッション (D1 に保存)。
  無料枠の CPU 10ms に収まらないため PBKDF2 パスワードは使わない。Cloudflare Access (無料 50 名) は代替案 (要確認: 無料登録にカード登録が要るか)
* プレビュー/サムネは Worker 経由で配信 (R2 バケットを公開しない)。アクセスが増えたら独自ドメイン配下の R2 公開に切り替え可能
* 画像処理は iPhone ブラウザ内 (サーバー費 0)。ZIP は「原本の CRC32 をアップロード時に保存」して Worker は無圧縮でつなぐだけ (CPU をほぼ使わない)

## 2. 無料枠の上限と超過時の費用

| サービス | 無料枠 | 超過時 | 本システムの想定 (1,000人/月 = 200 団体) |
|---|---|---|---|
| Workers | 10 万リクエスト/日、**CPU 10ms/リクエスト**、50 サブリクエスト | 無料枠は**超えると 429/エラーで止まる (課金されない)**。Paid $5/月: 1,000 万 req/月、CPU 30 秒 | 平常日 数千 req、ピーク日でも ~2 万 (TV 30 秒ポーリング 1,440/日 含む) |
| D1 | 読み取り 500 万行/日、書き込み 10 万行/日、保存 5GB (1 DB 500MB) | 無料枠超過はクエリがエラー。Paid: 読 $0.001/百万行、書 $1/百万行、$0.75/GB (Workers Paid が必要) | 写真 100 枚アップロード = 書込 約 300 行 (索引込み)。1 日 20 団体でも 6,000 行 |
| R2 | 保存 **10GB**、Class A 100 万/月、Class B 1,000 万/月、**転送料無料** | $0.015/GB・月、Class A $4.5/百万、Class B $0.36/百万 | 保存 約 16〜54GB → **従量費 約 14〜100 円/月** (これが唯一の変動費) |
| Cron Triggers | 無料枠内 | — | 1 本 (aone と別 Worker なので衝突しない) |
| Resend (メール) | 3,000 通/月、**100 通/日** | Pro $20/月 | 購入確認+期限案内で 1 注文 2〜3 通。aone と同じ Resend アカウントなら 100 通/日は**共有** |
| Stripe | 月額固定費なし | 手数料 3.6% (仮。契約で確認) | 売上に比例 |
| R2 の利用開始 | 無料枠でもクレジットカード登録が必要 (既存アカウントなら済) | — | — |

**無料枠が止まったとき**: 課金されず「止まる」ので、予期せぬ請求は起きない。代わりに販売が止まる。
そのため運用ルールとして管理画面ダッシュボードに「本日のリクエスト数 / 上限」を表示し、
**60% を超える日が続いたら Workers Paid ($5 ≒ 750 円) に上げる**。他サービスは上げる必要が出にくい。

### 0 円で運用できる条件
1. 1 日のリクエストが 10 万未満 (約 1,000 団体/日相当。本件の想定の数十倍の余裕)
2. 1 リクエストの CPU が 10ms 未満 — **最大のリスク。§3 の検証 (S1) を M1 の最初に行う**
3. R2 の従量費 (月 〜100 円) と Stripe 手数料は発生することを許容 (固定費ではない)
4. メールは 1 日 100 通以内 (aone との合算)

## 3. 技術リスクと検証ゲート

| # | リスク | 対策・検証 |
|---|---|---|
| S1 | **無料枠 CPU 10ms**: Astro の SSR、Stripe API 呼び出し、Webhook 署名 (HMAC)、署名付き URL (SigV4)、ZIP 配信が超えないか | M1 の最初に実装 → 本番相当で `wrangler tail`/ダッシュボードの CPU 時間を計測。**待ち時間 (fetch/R2/D1) は CPU に数えない**。超える処理だけ重いなら設計変更、全体的に超えるなら Workers Paid ($5) のみに上げる (D1/R2 構成は変えない) |
| S2 | ZIP (全パック 80 枚/240MB) | CRC32 を事前計算 + 無圧縮 (STORE) のため、Worker はバイト列をつなぐだけ。S1 で実測。ダメなら「写真ごとの保存ボタン + Web Share 一括保存」を主、ZIP を補助にする |
| S3 | D1 は対話型トランザクションが無い (batch が原子的) | 注文・決済確定は「条件付き UPDATE + 一意制約」で冪等に設計済み (`src/lib/shop/orders.ts`、テスト 11 項目) |
| S4 | D1 は 1 クエリ bind 100 個まで | 配列は `json_each(?)` で 1 パラメータに (注文明細で採用済み) |
| S5 | 無料枠超過で停止 | 上記の監視と 60% ルール。TV はキャッシュで継続表示 |
| S6 | RLS が無い | D1 は公開エンドポイントを持たず Worker からのみ。権限はコード側で検証 (他グループ写真の拒否・権限分離をテスト化) |

## 4. バックアップ・セキュリティ・障害復旧 (妥協しない項目)

### バックアップ (3 層)
| 層 | 内容 | 保持 | 費用 |
|---|---|---|---|
| 1. D1 Time Travel | 分単位の時点復元 (`wrangler d1 time-travel restore`) | 無料 7 日 / Paid 30 日 (要確認) | 0 |
| 2. 日次ダンプ → R2 | cron が D1 エクスポート API (読み取り専用トークン) を呼び、SQL ダンプを `aone-photo-backups` に保存 | 日次 14 世代 + 月次 12 世代 | 0 (数 MB) |
| 3. 別アカウント保管 | GitHub Actions (毎週) が `wrangler d1 export` → **age で暗号化**して Artifact / オーナーのストレージへ。リポジトリは公開なので**平文のダンプを置かない** | 90 日 | 0 |

* 写真 (R2): 耐久性は高いが、誤削除・バグ削除の救済は無い。原本の削除は cron のみに限定 (アプリ API からバケット全削除は不可)、
  削除は監査ログに残す。写真は保存期間が 30〜60 日で入れ替わるため別バックアップは取らない (購入済み写真だけ追加複製する案は要望があれば)
* **Stripe が支払いの正本**: 管理画面に「Stripe と照合」を用意 (直近の Checkout Session と注文を突き合わせ、DB 復旧後の欠落注文を再構築)。
  Checkout の metadata に order_id を入れる

### セキュリティ
* 公開 DB 端点なし / 秘密値は Worker シークレット / 原本は公開 URL 無し・Worker が paid を確認して返す
* QR は 128bit トークン、他グループ写真 ID は拒否、同意の無いグループは DB の CHECK で公開不可
* Webhook は署名検証 + 冪等 (同じ payment_intent は 2 回記録不可)、ダウンロード権限は注文ごと

### 障害復旧 (手順書は M8 で運用マニュアル化)
| 障害 | 復旧 | 目標 |
|---|---|---|
| Worker のバグデプロイ | `git revert` → 再デプロイ (または Dashboard でロールバック) | 10 分 |
| D1 の誤更新・破損 | Time Travel で直前時刻へ復元 → (不可なら) 日次ダンプから `d1 execute --file` | RPO ≒ 0〜24h、RTO 〜1h |
| D1 が空/消失 | 新 D1 作成 → マイグレーション → ダンプ import → Stripe 照合で欠落分補完 | RTO 数時間 |
| 無料枠停止 | 翌日 0:00 UTC (JST 9:00) にリセット、または Paid に変更 (即時) | 即時〜翌朝 |
| Cloudflare 障害 | 待つ。TV は端末キャッシュで継続表示、販売は停止 | — |
| アカウント喪失 | 層 3 のダンプ + コード (GitHub) + Stripe 履歴から再構築 (写真は失われる) | 日 |

## 5. Supabase 無料プランとの比較

| 項目 | **D1 + R2 + Workers (推奨)** | Supabase Free + R2 + Workers |
|---|---|---|
| 固定費 | 0 円 | 0 円 (本番で安定させるなら Pro $25 ≒ 3,750 円) |
| DB 容量 | 5GB (1 DB 500MB) | 500MB |
| 停止 | 無し | **7 日無操作で一時停止** (営業日は毎日使うが、休業・天候中止が続くと危険) |
| バックアップ | Time Travel (7 日) + 自前ダンプ | **無料プランに自動バックアップ無し** (自前 pg_dump が必須) |
| 認証 | 自作 (メールリンク) | Supabase Auth |
| ロジック | TypeScript + 条件付き SQL (テスト済み) | PL/pgSQL + RLS |
| 公開される DB 端点 | 無し | 有り (anon key + RLS の設定ミスが事故になる) |
| 別サービス数 | Cloudflare に一本化 | Cloudflare + Supabase の 2 つ (障害点が増える) |
| 既存 aone との連携 | HTTP API で連携 (将来) | 同じ Postgres 流儀 (ただし別プロジェクト) |
| 開発の手間 | 既に移行済み (下記) | Postgres 案を維持するなら追加作業無し |
| 将来 Pro が必要になる線 | Workers Paid $5 のみ | Pro $25 |

判断: 売上が読めない新規サービスで「停止しない・バックアップが付く・固定費が 0」を満たすのは D1 案。

## 6. PostgreSQL → D1 移行 (変更箇所・工数・リスク)

M0 の段階でまだ実装コードが無く、移行は**スキーマとロジックの書き換えのみ**で、すでに完了している (`app/migrations/0001_init.sql`、`src/lib/shop/`、テスト)。

| 変更箇所 | 内容 | 工数 (実績/見積) |
|---|---|---|
| 型 | uuid→TEXT (randomblob)、timestamptz→ISO 文字列、jsonb→TEXT+json_valid、boolean→INTEGER、generated 列はそのまま | 済 |
| 関数 | `photo_calc_price` / `photo_create_pending_order` / `photo_finalize_order` / 返金 / 削除対象 → TypeScript | 済 (テスト 11 項目) |
| ロック | `pg_advisory_xact_lock` 廃止。複数人購入可のため直列化が不要に。冪等は条件付き UPDATE と一意制約 | 済 |
| 配列 | `uuid[]` → `json_each(?)` | 済 |
| RLS/GRANT | 廃止 (公開端点が無いため) | 済 |
| 認証 | Supabase Auth → メールリンク + sessions テーブル | M1 に 1.5 日 |
| バックアップ | Time Travel + cron ダンプ + 週次暗号化コピー | M7 に 1 日 |
| **リスク** | ① 無料枠 CPU 10ms (S1) ② D1 は同時実行時に Postgres のような行ロックが無い (設計で回避、同時実行の自動テストは node:sqlite の同期実行のため**本物の並行は再現できない**。本番相当の負荷試験を M8 で実施) ③ SQLite の型が緩い (CHECK で補強) ④ 将来 Postgres に戻す場合の再移行 (小さな DB なので 1 日程度) | |

旧 Postgres 案は `db/archive-supabase/` に退避 (更新しない)。
